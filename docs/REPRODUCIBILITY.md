# Reproducibility — Dhaka Smart Waste V4.0

## 1. What is reproducible

The canonical dataset is generated by `generate_v4_0.py` from fixed code, fixed scenario tables and a fixed NumPy pseudorandom seed:

```text
SEED = 20260902
```

Expected canonical dimensions:

```text
Bins:             5,000
Days:               365
Hours per bin:     8,760
Observations: 43,800,000
Timezone: Asia/Dhaka (UTC+06:00)
Period: 2025-01-01 00:00 through 2025-12-31 23:00
```

The generator produces:

```text
dhaka_smart_waste_v4_0_2025.h5
```

The canonical HDF5 file is validated by `validate_v4_0.py`.

The public observation release is partitioned into 92 Parquet observation files and a separate `bins.parquet`.

Required Python packages:

```text
numpy
h5py
pandas
thrift
```

Roles:

- `numpy`: pseudorandom generation and vectorized simulation
- `h5py`: canonical HDF5 storage
- `pandas`: validation/calendar aggregation
- `thrift`: lightweight Parquet-footer row-count validation in `validate_export_parts.py`

The generator itself uses Python standard-library modules plus NumPy and h5py. Validation additionally uses pandas. The release-layout validator uses thrift.

The supplied code does not require CUDA or a GPU.

## 4. Hardware, runtime and storage disclosure

The exact hardware model, peak RAM use and wall-clock duration of the original full generation were not preserved in the release metadata. They should therefore not be reported as measured values.

What can be stated from the implementation:

- generation is CPU-, memory- and disk-I/O-intensive because 43.8 million hourly observations are produced;
- no GPU-specific library is used or required by the supplied generator/validators;
- enough free local storage is needed for the canonical HDF5 file and any exported Parquet copies;
- the 23 current Parquet transport ZIPs together are approximately 1.92 GB, but full regeneration requires additional working storage beyond the compressed public release size.

For a new reproducibility run, record:

```text
CPU model
physical RAM
operating system
Python version
package versions
start time
finish time
peak or observed storage usage
```

## 6. Clean reproduction procedure

### Step 1 — create an isolated environment

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Windows PowerShell:

```powershell
py -3 -m venv .venv
.venv\Scripts\Activate.ps1
```

### Step 2 — upgrade installer tooling

```bash
python -m pip install --upgrade pip
```

### Step 3 — install dependencies

```bash
python -m pip install -r requirements.txt
```

### Step 4 — capture the exact environment used for this run

```bash
python -m pip freeze > environment_lock.txt
python capture_environment.py > environment_summary.txt
```

### Step 5 — generate the canonical dataset

```bash
python src/generate_v4_0.py
```

Expected canonical output file:

```text
dhaka_smart_waste_v4_0_2025.h5
```

The final console output should report creation of the HDF5 file. The generator also asserts internally that the final write position equals exactly:

```text
43,800,000 rows
```

### Step 6 — run the full canonical-state validation

```bash
python scripts/validate_v4_0.py
```

Expected validation artifact:

```text
VALIDATION_REPORT.json
```

Mandatory structural expectations include:

```text
rows = 43,800,000
bins = 5,000
days = 365
hours_per_bin = 8,760
```

The validation additionally checks composition integrity, collection-label consistency, global telemetry rates, scenario patterns and monthly climate behavior.

### Step 7 — verify the public Parquet reconstruction/export

Place the reconstructed public release under:

```text
final_parts/
└── PARQUET/
    ├── bins.parquet
    ├── observations_part_000.parquet
    ├── ...
    └── observations_part_091.parquet
```

Then run:

```bash
python scripts/validate_export_parts.py final_parts
```

Expected output:

```text
PASS
Parquet observation parts: 92
Parquet rows: 43800000
Parquet first/last rows: 480000 120000
```

The expected partition layout is:

```text
parts 000–090: 480,000 rows each
part 091:       120,000 rows
total:       43,800,000 rows
```

### Step 8 — validate the distributed transport release

When validating the released Drive layout containing 23 Parquet transport ZIPs plus `PARQUET_PARTS/bins.parquet`, use the publication-oriented validator:

```bash
python -m pip install -r requirements-validation.txt
python scripts/validate_v4_0_paper.py \
  --project-root "/path/to/Dhaka Smart Waste V4.0 2025" \
  --extract-dir "/tmp/dhaka_smart_waste_v4_validation" \
  --output-dir "/path/to/VALIDATION_OUTPUTS"
```

The successful 22 September 2026 release-level run scanned all 43,800,000 hourly rows and produced the artifacts mirrored in `validation/`.

## 7. Release-level validation checklist

A release should not be treated as complete until all of the following are true:

- [ ] `bins.parquet` is present
- [ ] observation parts `000` through `091` are all present
- [ ] all 92 Parquet files have readable Parquet footers
- [ ] parts `000–090` each contain 480,000 rows
- [ ] part `091` contains 120,000 rows
- [ ] total hourly rows equal 43,800,000
- [ ] canonical validation reports no mandatory structural failure
- [ ] the eight residual composition percentages sum to 100 for every canonical observation
- [ ] `needs_collection` agrees with the documented threshold rule
- [ ] release documentation and data dictionary match the exported schema

For transport, the 92 observation files are grouped into 23 ZIP archives. The ZIP grouping is only packaging and does not change the logical partition layout.

## 9. What exact reproducibility means here

With unchanged source code, fixed seed, fixed dependency behavior and the same numerical/software stack, the simulation is intended to reproduce the same pseudorandom state and generated dataset.

For best reproducibility, save an exact environment lock file for each full regeneration and verify the outputs using the supplied validators.

Scientific/structural reproducibility should be reported using:

1. fixed generator source;
2. fixed seed;
3. recorded environment for the rerun;
4. exact row/bin/partition counts;
5. validation-report checks;
6. release-level Parquet integrity checks.

## 10. Transparency note

The data are a scenario-based synthetic digital twin, not field sensor measurements.

The external evidence base supports selected calendar, climate and waste-system anchors. Fine-grained hourly multipliers, sensor-fault rates, recovery-rate ranges and similar coefficients are explicit simulation assumptions. Reproduction of the dataset does not constitute empirical validation of those assumptions.

## 11. Reviewer-oriented full-release validation

A separate full-release validator was run against the distributed Parquet package on 22 September 2026. It scanned all **43,800,000** hourly observations and all **92** logical Parquet parts, with **0 duplicate** and **0 missing** bin-hour keys. The automated gate reported **49 hard checks PASS**, **15 soft checks PASS**, **0 hard failures**, and **0 warnings**.

Publication-oriented validation artifacts are maintained under `validation/` on the repository main branch, including the check summary, ZIP-to-Parquet mapping, SHA-256 release manifest, environment summary, monthly climate table, scenario summaries, and technical-validation draft. These checks establish structural/rule consistency and reproducibility of the synthetic release; they are not field validation of deployed municipal smart bins.
